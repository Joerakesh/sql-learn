# SQL Indexes Demo: 10 Million Records

A hands-on MySQL demo that shows **what an index is, why it is used, and what it costs**, using a table of 10,000,000 students. With 10 rows you cannot feel the difference between a slow and a fast query. With 10 million rows you can.

## What is an index?

An index is a separate data structure (a B-tree in MySQL's InnoDB) that lets the database find rows without reading the whole table. It works like the index at the back of a book: instead of reading every page to find a topic, you look it up and jump straight to the right page.

| Without an index | With an index |
| --- | --- |
| MySQL reads every row (full table scan) | MySQL jumps directly to the matching row(s) |
| Slower as the table grows | Stays fast even on huge tables |

## Why use indexes?

- Speed up `WHERE` searches
- Speed up `JOIN`s, `ORDER BY` and `GROUP BY`
- Enforce uniqueness (`UNIQUE` index)

## What is the cost?

- Extra disk space for every index
- Slower `INSERT`, `UPDATE` and `DELETE`, because the index must be updated too
- Building an index on an existing large table takes time

**Rule of thumb:** index columns you frequently search, join or sort by. Do not index everything.

1. Open `index_demo.sql` in MySQL Workbench.
2. Run **Part 0** to create the database, tables and load the data.
3. The load runs in 10 batches of 1 million rows and takes a few minutes.
4. Check the load with:


**If the connection drops** (Error 2013), raise the timeout in
`Edit > Preferences > SQL Editor > DBMS connection read timeout` to `600`, then reconnect.

## Table structure

```sql
students_million (
    student_id   INT PRIMARY KEY,
    student_name VARCHAR(100),
    department   VARCHAR(50),    -- 4 distinct values
    city         VARCHAR(50),    -- 5 distinct values
    email        VARCHAR(150),   -- unique per student
    cgpa         DECIMAL(4,2)
)
```

## Demo flow

| Part | What you show | What to point out |
| --- | --- | --- |
| 1A | Search by `student_id` | The primary key is already indexed, so it is instant (`type = const`) |
| 1B | Search by `email` **before** an index | Full scan: `type = ALL`, `key = NULL`, ~10M rows, takes seconds |
| 2 | `CREATE UNIQUE INDEX idx_email` | Building the index takes time and disk space |
| 3 | Same email search **after** the index | `type = const`, `key = idx_email`, `rows = 1`, near instant |
| 4 | Index on `department` | Only 4 distinct values, so ~2.5M rows match. MySQL may still choose a full scan |
| 5 | `DROP INDEX` | Indexes have a cost; clean up and repeat if needed |

## Reading `EXPLAIN`

| Column | Meaning |
| --- | --- |
| `type` | How MySQL accesses the table. `ALL` = full scan (bad), `const`/`ref` = index lookup (good) |
| `possible_keys` | Indexes MySQL could use |
| `key` | Index MySQL actually chose (`NULL` = none) |
| `rows` | Estimated rows MySQL must examine |

## Key takeaways

1. An index turns a full table scan into a direct lookup.
2. Primary keys are indexed automatically.
3. A `UNIQUE` index speeds up searches and also prevents duplicates.
4. Indexes work best on **high-selectivity** columns (many distinct values, few matching rows), such as email or ID.
5. Indexes on low-selectivity columns (such as department) help far less.
6. Every index costs storage and slows down writes.
7. Use `EXPLAIN` to check whether an index is really being used.
